# Atlas AAC project guide

## Project layout

- The application is in `atlas/`. Run package and Expo commands from that directory.
- This is an Expo SDK 54 / React Native 0.81 app using TypeScript, Expo Router, Zustand, Firebase Authentication, and React Native Web.
- `atlas/app/` contains file-based routes. `app/_layout.tsx` loads fonts, provides navigation theme and auth, then protects login and signed-in routes. `app/(tabs)/_layout.tsx` defines the tabs.
- Main screens: `(tabs)/index.tsx` (Speak/AAC sentence builder), `board.tsx` (drawing/photo/word board), `transcribe.tsx` (speech recognition and conversation history), `settings.tsx`, and `emotions.tsx` (hidden tab route).
- Shared UI lives in `components/`; app-wide tile and settings state is in `state/`; tile data and visual/layout tokens are in `constants/`; integrations are in `services/`; helpers are in `utils/`.
- `native/ios` and `native/android` hold SmartSpectra integration examples, not generated native app projects. The actual `ios/` and `android/` folders are ignored/generated by Expo prebuild.

## Setup and commands

```sh
cd atlas
npm ci
npm run start
```

Available package scripts (from `atlas/`):

- `npm run start` — start Expo/Metro.
- `npm run android` — run the Android native app (`expo run:android`).
- `npm run ios` — run the iOS native app (`expo run:ios`).
- `npm run web` — start the web target.

There are no `test`, lint, or typecheck scripts defined in `atlas/package.json`. Do not assume a test suite exists; use a targeted verification command when the task calls for verification. `atlas/tsconfig.json` enables strict TypeScript and maps `@/*` to the `atlas/` root.

## App architecture and data flow

- Routes are Expo Router files under `atlas/app/`. Keep auth and top-level providers in `app/_layout.tsx`; screen-specific UI and interactions belong in the route.
- `state/useAacStore.ts` owns tiles, the current sentence, folder navigation, and deterministic suggestions. `state/useSettingsStore.ts` owns selected language, translated tiles, and accessibility/emotion toggles. Both use Zustand and are currently in-memory stores; do not imply their values persist across launches.
- Tile definitions and general-word buckets are derived from `constants/tiles.json` by `constants/tiles.ts`. `Tile` includes stable `id`, `label`, `color`, optional `parentId`, `isFolder`, `speechText`, and `imageUrl`. Keep folder membership and IDs consistent when editing vocabulary.
- `utils/suggestions.ts` suggests sibling tiles and then a fixed fallback list. It is not a learned prediction model.
- The Speak screen and other routes call `services/openrouter.ts` for AI operations, `services/opensymbols.ts` for symbol search/cache, and native `expo-speech`/`services/elevenlabs.ts` for speech. Preserve a usable fallback when optional network services are unavailable.
- The Board screen uses `components/InfiniteBoard.tsx`, `DrawingCanvas.tsx`, and `utils/drawingToImage.ts`; it supports placed tiles/photos/drawings and can request interpretations from OpenRouter.
- Transcribe uses `services/speechRecognition.ts` (browser `SpeechRecognition` support), OpenRouter simplification/replies/tile mapping, and AsyncStorage for up to 50 saved conversations. Speech recognition support varies by browser/platform.
- `services/firebase.ts` configures Firebase Auth and Google sign-in. `state/AuthProvider.tsx` exposes the auth state; protected routes are set in the root layout.
- `components/EmotionDetector.tsx` and `EmotionCamera.tsx` have platform-specific `.web.tsx` variants. Check both implementations when changing cross-platform behavior.

## Implemented behavior versus design notes

The root `README.md` is a long personalization-engine concept document, not an accurate specification of shipped code. Do not treat its collaborative filtering, Markov prediction, GPS/BLE context, festival intelligence, federated learning, cloud sync, model retraining, or performance metrics as implemented. Current suggestions are deterministic; `services/ai.ts` is a placeholder, while active AI calls are in `services/openrouter.ts`. `utils/translation.ts` calls `http://localhost:8244/translate`; translation therefore depends on a separate local service and falls back to source text. The SmartSpectra native files are commented examples with manual setup notes, not a wired Expo native module.

## Configuration and integrations

- Local environment files are gitignored. `atlas/config/api.ts` reads `EXPO_PUBLIC_OPENROUTER_API_KEY`, `EXPO_PUBLIC_OPENSYMBOLS_SECRET`, and `EXPO_PUBLIC_ELEVENLABS_API_KEY`. `atlas/services/firebase.ts` reads `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` for native Google sign-in. See `atlas/AUTH_SETUP.md` and `atlas/firebase.env.example` for auth setup.
- Expo `EXPO_PUBLIC_` values are embedded in client bundles. Never put private server credentials there, commit `.env` files, or print key values to logs. Treat any existing key logging as sensitive and avoid expanding it.
- OpenRouter calls use `services/openrouter.ts`; OpenSymbols requests and persistent symbol cache use `services/opensymbols.ts`; ElevenLabs speech is in `services/elevenlabs.ts`. Keep configuration centralized and handle missing keys/network/API errors without crashing screens.
- Translation currently assumes the local endpoint at port 8244. Do not silently treat it as a deployed or bundled backend.
- Google sign-in on native requires a development/native build and platform OAuth/Firebase setup; it does not work in Expo Go. Follow `atlas/AUTH_SETUP.md` before changing sign-in setup.

## Change conventions

- Prefer the existing TypeScript, React Native, Expo Router, and Zustand patterns. Use `@/` imports for app-root modules.
- Keep `.web.tsx` platform alternatives aligned with their native/default component when changing shared behavior.
- Preserve accessibility/readability features: large touch targets, clear labels, theme tokens from `constants/Colors.ts`, and font selection through `components/FontText.tsx` where used.
- Keep AAC speech output faithful to the selected tiles and board context. Do not add inferred words to a user's message without an explicit product requirement.
- Update the relevant setup documentation when changing environment variables, native configuration, or developer commands. Do not edit lockfiles by hand.
- Before adding dependencies, check the existing Expo-compatible packages and use the package manager/lockfile already present in `atlas/`.
